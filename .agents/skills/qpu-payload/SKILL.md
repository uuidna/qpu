# QPU · payload

Payload's plugin schema as the one shape of every result: nested docs of lexical documents whose blocks are programmable UUID logic, SEO from the block, no custom collection, a few kilobytes computed once

Generated by `payload { scripts: { skills: true } }` from the toolbox itself (2 tool(s), 100 example(s), 3 direction(s)); edit the toolbox, never this file.

## How a client uses it

configure: a client calls it with no kind to test every configuration around the torus, with kind and current (its file text) to learn the drift as leads, with kind tenant and the names of its environment to learn what the operator still has to set; gen-docs writes the manifest from kind pwa. A Payload host with the default plugins (lexical, nested-docs, seo) stores _meta.payload of any result as it is: the lexical field is the document, nestedDocs.parent the parent relation, seo the plugin's fields; the block's uuid is the id. A device renders the block from its uuid alone (the walk) and never recomputes what the balancer computed.

## Register

This skill is one UUID (ISO/IEC 9834-8): `4bb54909-bf63-1321-ac94-2c5f375bb491`, sealed, a register of 122 qubits at hexbit width 4 (32 × 4 − 4 − 2 = 122). The QPU computes the address from the skill's own text (uuid of its canonical text: name, idea, instructions, directions, tool names, ISO clauses); a changed toolbox is a different address, so the skill is verified by recomputing it.
